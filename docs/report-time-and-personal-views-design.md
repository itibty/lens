# Lens 报表时间与个人视图：两个迭代设计

日期：2026-09-15

状态：两个迭代已实现，分支 `codex/report-time-personal-views`
目标用户：企业内部业务人员查看报表，少量分析人员制作报表。

## 1. 已确认的范围与建议

- 迭代一：刷新时间、由分析人员配置 SQL 的业务数据更新时间，以及刷新失败状态。
- 迭代二：常用报表入口、收藏、个人视图（先支持筛选）、订阅携带视图条件。
- Tab、图例选择纳入个人视图模型的扩展设计，本次不实现它们的保存与恢复。
- 本文将“订阅截图带订阅”理解为：订阅截图携带订阅时选择的筛选／视图条件。

核心划分：

| 层次 | 保存什么 | 谁管理 |
| --- | --- | --- |
| 报表定义 | 数据集、卡片查询、布局、筛选器定义及公共默认值 | 分析人员 |
| 个人视图 | 用户选择的筛选值；以后扩展 Tab、图例选择 | 当前用户 |
| 查询状态 | 本次是否成功、结果生成时间、源端更新时间 | 系统运行时 |

个人视图不复制看板或卡片，也不保存查询结果；打开时使用当前报表定义和当前权限重新查询。

## 3. 迭代一：刷新时间与数据更新时间

### 3.1 时间的定义

| 用户文案 | 含义 | 来源 |
| --- | --- | --- |
| 最近刷新 | 当前展示结果最近一次成功取数的完成时间 | 后端在整个卡片查询成功后生成 |
| 数据更新于 | 分析人员定义的源端业务数据更新时间 | 数据集配置的 SQL |
| 数据截至（可选文案） | 源端明确保证覆盖到哪个业务时间 | 同一 SQL 机制，但由分析人员明确选择这个含义 |

例如：`最近刷新 10:32:08 · 数据更新于 09:00`。

“数据更新于”与“数据截至”是不同口径的可选标签，一项配置选择一种；不能自动把最大订单日期或最大修改时间解释为完整数据截止时间。SQL 查到 `MAX(updated_at)` 只说明最后一条记录的修改时间。

现有 `modifyAt` 表示配置修改时间，`asOfDate` 表示相对日期计算基准，都不能代替上述时间。订阅现有 `generatedAt` 则只表示邮件／截图生成时间。

### 3.2 配置放在数据集

数据集编辑增加“数据更新时间”配置区：

1. 是否启用，默认关闭；关闭时前台不显示业务数据时间。
2. 时间含义：数据更新于／数据截至，默认数据更新于。
3. 时间精度：日期／日期时间；无时区时间的解释时区默认 `Asia/Shanghai`。
4. 查询 SQL：使用该数据集的数据源，返回一行一列，建议固定列别名 `data_time`。
5. 测试按钮：展示解析后的时间和明确的错误原因。

推荐从成功同步批次表查询；没有批次表时，分析人员可选择合适的业务表字段。此 SQL 独立于主查询，可以查询同一数据源中的批次表，不必把更新时间混入维度和指标。

执行约定：

- 本期是数据集口径，不随页面的地区、日期等筛选改变。配置说明必须写明这一点。
- 可以复用服务端提供的用户上下文，不能让普通查看者传入任意 SQL、数据源或系统身份参数。
- 仅数据集配置权限可修改或测试 SQL；查看态只得到时间和状态。
- 限制为只读取数，短查询超时（建议 3 秒，可由系统配置）和最多两行探测，多行／多列明确报错；仅限制返回行数无法限制扫描成本。
- 0 行、NULL：未知；非法时间、多行多列、查询失败：获取失败。不能用当前时间补齐。
- 同用户、同数据集、同配置只合并正在执行的时间查询；不缓存查询结果，配置变更后使用独立请求。

### 3.3 取数和状态模型

建议普通、明细和透视响应都带一个共用 `queryMeta`：

```ts
interface QueryMeta {
  resultGeneratedAt: string // ISO 8601，服务端生成，包含时区
  dataTime: {
    status: 'disabled' | 'ok' | 'unknown' | 'error'
    kind?: 'updatedAt' | 'coverageEnd'
    value?: string          // 日期保留 YYYY-MM-DD；时间包含时区
    precision?: 'date' | 'datetime'
    timezone?: string
    checkedAt?: string     // 源端标记实际查询时间，详情中展示
  }
}
```

这里的类型是拟议接口，不直接修改生成的客户端。后端变更后统一运行 `pnpm generate-api`。

实现建议：新增数据时间服务，读取数据集的配置；卡片主查询成功后组装上述元信息。同一用户、同一数据集配置的并发检查合并，避免一屏卡片重复查询时间 SQL。本期不增加查询结果缓存或独立定时同步任务；若实施时需要短缓存，必须按用户和配置版本隔离，并返回真实 `checkedAt`。

业务主查询与时间 SQL 分别读取，时间是源端标记，不能宣称它们或不同卡片处于同一个数据库快照。时间 SQL 失败不应导致成功的图表数据丢失。

前端每卡维护：查询状态、最近尝试、最后成功的数据和元信息、刷新错误、查询条件指纹、请求序号。

| 情形 | 数据与时间行为 |
| --- | --- |
| 首次取数成功 | 同时提交数据及本次元信息 |
| 首次失败 | 展示错误，不产生“最近刷新” |
| 同一条件刷新中 | 保留现有数据和时间，显示正在刷新 |
| 同一条件刷新失败 | 保留旧数据及其原时间，显示“更新失败，仍显示 10:32 的结果”，可重试 |
| 筛选条件改变 | 旧数据不得被当作新筛选结果展示；本期推荐清空并加载新结果 |
| 时间 SQL 失败、图表查询成功 | 最近刷新推进，业务数据时间显示获取失败 |
| 过期请求晚到 | 数据、时间、状态一并忽略 |
| 静态卡片 | 不显示取数时间，也不纳入查询统计 |

静默刷新只影响加载动画，不代表隐藏失败。未来加入缓存时，缓存命中也不能把 `resultGeneratedAt` 改成请求到达时间。

### 3.4 页面展示

**卡片**：操作区使用无边框、无底色的时间小图标；悬停或键盘聚焦查看业务数据时间和查询刷新时间，触屏点击展开。失败时显示短提示，保留旧结果及原时间。

**看板**：不单独提供时间汇总入口。刷新按钮反馈加载状态；存在失败时显示提示标记，悬停给出失败数量，点击重试。

- 卡片独立取数，不简单取最大时间并标成“整个看板已刷新”。
- 因为有懒加载和 Tab，状态只统计已加载的卡片，隐藏 Tab 不算查询成功或失败。
- 不把不同数据集的时间取最大／最小值后统一称为数据更新时间。
- 业务数据时间归属具体卡片；截图按数据集保留时间口径，不合成为一个看板时间。

**截图与订阅**：时间属于报表信息，不应随操作工具栏一起被截图隐藏。迭代一就增加紧凑的截图说明区：生成时间、各数据集时间／未知状态。业务查询失败仍沿用拒绝发送的行为；仅时间 SQL 失败，可发送并明确标注时间获取失败。

### 3.5 数据库与落点

- `vis_dataset` 增加 `data_time_config_json`（可空），保存启用、口径、精度、时区、SQL。
- 修改数据集相关 DTO、服务、编辑页；SQL 不进入普通用户查询响应。
- 增加后端共用时间 DTO／数据时间服务，接入 `VisDataService` 和 `PivotDataService`。
- 改造 `useVisCardQuery`，将时间与数据作为一次成功结果提交。
- 增加按卡片标识维护的看板状态汇总；现有 `dashQueryTracker` 继续负责等待，不能把“Promise 已结束”视为“查询成功”。
- 更新卡片、看板及截图中的时间展示。
- 查询时间是运行状态，不为每次刷新新增数据库历史记录。

### 3.6 验收重点

- 查询成功但源端数据未更新时，刷新时间推进，数据更新时间保持不变。
- 自动／手动刷新失败都显示旧结果时间；首次失败不出现伪成功时间。
- 切换筛选、快速重复刷新、切换看板时，没有错配或过期时间覆盖。
- 时间 SQL 空结果、NULL、错误类型、超时、不同精度／时区均有确定行为。
- 多数据集、懒加载、隐藏 Tab、静态卡片的汇总不夸大“全部完成”。
- 截图和邮件保留时间说明；元数据异常与业务查询异常分别处理。

## 4. 迭代二：常用报表、个人视图与订阅

### 4.1 先统一用户概念

| 概念 | 行为 | 是否保存筛选 |
| --- | --- | --- |
| 收藏报表 | 从报表更多菜单收藏，或在首页列表点击星标 | 否 |
| 常用报表 | 个人入口，先包含“我的收藏”和“最近访问” | 否 |
| 个人视图 | 给当前查看状态起名字，按需设为该报表的个人默认视图 | 是 |
| 订阅视图 | 创建／更新订阅时复制的查看状态 | 是，独立快照 |

首页沿用原插图，下方放“收藏”和“最近访问”两个紧凑列表，不设置页面大标题。桌面并列、窄屏上下排列。通过 logo 或报表工作区入口进入首页，侧栏只展示授权报表分组，不添加“我的报表”虚拟菜单。列表可直接打开报表或修改收藏，最近访问显示访问时间，不引入频次算法。

收藏与个人视图相互独立：取消收藏不会删除个人视图；创建个人视图也不隐式收藏报表。

### 4.2 交互

看板标题行右侧依次放视图切换、刷新与更多菜单，收藏收进更多菜单。操作区默认收起，悬停顶栏、键盘聚焦或触屏点按顶栏时显示；菜单展开期间保持可见，触屏点按外部或滚动后收起。收起仅淡出，不改变布局。筛选始终展示在下一行，过多时换行。

更多菜单使用两列操作区，主题预览四列两行；说明最多展示两行，悬停可查看完整内容。菜单布局、主题与操作项由独立组件管理，顶栏保留事件转发和可见性控制。

视图菜单：

- 原始视图（分析人员配置的报表默认状态）。
- 当前用户保存的视图，例如“华东门店”“线上渠道”。
- 上方展示可选视图，当前项高亮并显示勾选，默认项用“默认”标记。
- 底部独立展示保存按钮与管理入口；管理菜单包含重命名、设为默认／取消默认、复制筛选链接、删除等操作。

选择筛选后用圆点标记未保存状态，已选个人视图时保存按钮变为“保存修改”。临时浏览不自动覆盖保存的个人视图；更新／另存为由用户显式执行。视图只有查看状态，不包含布局编辑和卡片 SQL。

个人默认是“这个用户在这张报表上的默认”，不影响其他用户。点击“恢复报表默认”时，本次明确采用公共默认值，不能又被个人默认覆盖；也不直接删除个人默认设置。

最近访问只记录成功打开报表，一次访问内的自动刷新和筛选变化不计入新访问；同一用户／报表记录可节流更新，排序使用最后访问时间。订阅截图、测试发送、设计器预览不算业务人员访问。

### 4.3 用统一的视图状态承载扩展

第一版状态：

```json
{
  "schemaVersion": 1,
  "filters": {
    "f-region": { "value": ["华东"] },
    "f-date": { "valueExp": "last_day" }
  }
}
```

`filters` 复用现有筛选值结构；存已应用的值，不保存筛选弹层中尚未确认的草稿。显式清空与不存在必须区分：清空阻止默认值重新填入，不存在才继承新定义的默认值。

此外在服务端保存筛选绑定的语义签名（数据集、字段、用途 filter／param、操作符、时间粒度和类型），与现有定义核对；不能只凭相同 uid 就认定含义未变。改标签不应使视图失效。

未来可新增独立命名空间并升级 schema：

```json
{
  "tabs": {
    "g-sales": { "activeCardId": "9208" }
  },
  "legends": {
    "9208": {
      "channel": { "excludedValues": ["线下"] }
    }
  }
}
```

这些是扩展方向，不是本期已支持字段：

- Tab 按稳定的分组 ID + 卡片 ID 保存；当前 page ID 在编辑时可能重建。
- 图例按卡片 ID、图例对应的稳定业务键和值保存，不按颜色、显示标题或图中序号保存。
- 图例“隐藏系列”属于展示状态，默认不改变其他卡片、明细或后端导出的取数范围；将来如需数据过滤，应定义独立行为。
- `excludedValues` 表示隐藏这些值，新出现的系列默认显示；其他选择语义将来另行定义。
- 当前看板不允许重复卡片，card ID 可定位图表；将来允许重复实例时再增加稳定实例 ID。
- 不保存 hover、tooltip、加载动画、滚动位置、查询结果、刷新时间或账号 Token。

前端建议新增 `useDashboardViewState` 和共用 codec。提供收集、标准化、验证、应用、比对能力，让 URL、个人视图和订阅统一使用，不各自拼接条件。

### 4.4 打开优先级与兼容性

打开时选择一个状态来源：

1. 订阅运行的明确快照（专用截图／邮件回看入口）。
2. URL 显式携带的状态，含旧 `f` 参数。
3. URL 明确指定的个人视图。
4. 用户在此报表设置的个人默认视图。
5. 报表公共默认值。

显式来源之间不混合，个人默认不能污染分享链接或订阅快照。所选状态允许用当前公共默认值补齐没有保存的新字段，但要先通过兼容性检查。

普通打开时：

- 已删除的视图或无权访问的视图明确提示，不悄悄改用另一个个人视图。
- 字段被删除、数据源／绑定变更、类型不兼容：提示“视图需要更新”，用户确认兼容部分后再应用。不能无提示丢掉限制条件后查全量。
- 下拉枚举当前查不到旧值，不代表筛选非法；可能只是该值已无数据，仍应保留精确筛选并返回空结果。
- 读取更高版本、尚不支持的视图时提示不支持，不静默删掉未来字段再覆盖保存。
- 保持旧 `f` 链接可读；新链接走相同校验流程。只保存了个人视图 ID 的链接仍只属于该用户，“复制当前状态链接”携带值并由接收者按自己的权限查看。

### 4.5 订阅复制视图快照

创建订阅表单增加“订阅内容”：

- 当前查看状态，默认选中；显示例如“地区：华东；时间：昨天”。
- 报表默认视图。
- 从某个已保存个人视图载入条件。

无论选择哪项，都在保存时生成一份独立状态快照，覆盖当前已有筛选器的有效值，包括显式清空。用户可明确更新订阅内容，系统不会随个人视图的后续修改自动改变订阅。

因此：

- 修改／删除个人视图：已保存订阅继续使用自己的条件。
- 修改订阅条件：后续新运行使用新快照，已入队运行保持自己的快照。
- 看板、字段和权限发生变化：运行时重新校验；快照不授予历史权限，也不冻结看板 SQL 和布局。
- 旧订阅没有快照：明确标为“跟随报表默认（旧订阅）”并保持既有行为；编辑时选择内容后转为快照。每次旧订阅入队仍将当时默认条件固定到运行记录。

相对日期规则：

- 订阅配置保存“昨天／上周”等表达式。
- 首次领取运行时，按订阅时区和实际执行日期确定一个统一基准，并保存日期基准，查询与回看按同一基准解析日期范围；手动测试也遵循此规则。
- 同一运行的所有卡片和重试使用同一个日期基准；不能跨午夜后每张卡各算一个“昨天”。
- 现有卡片 `query.asOfDate` 可能固定日期。订阅运行的基准必须覆盖截图上下文内的相对日期解析，包括普通、透视、筛选参数及同环比；显式绝对日期保持不变，原卡片配置不改写。
- 停机恢复采用现有“只补一次”策略，本期按实际执行日解释相对日期，并在运行记录中保留计划时间与实际日期基准；不把旧计划日伪装成实际业务日期。

邮件链接使用本次运行保存的条件与固定日期基准，打开后按当前权限重新查询。它复现的是条件，实时数据可能与历史截图不同，界面需注明这一点。

### 4.6 截图流程

```mermaid
flowchart LR
    A[个人视图或当前筛选] --> B[订阅配置快照]
    B --> C[入队时复制运行快照]
    C --> D[领取时固定日期基准]
    D --> E[以订阅所有者身份校验并恢复状态]
    E --> F[查询当前需要展示的卡片]
    F --> G[检查成功状态与渲染完成]
    G --> H[截图及发送]
```

具体约束：

- 截图服务传递运行 ID，由后端在订阅所有者权限下读取运行快照；不允许普通用户提交任意 owner ID 执行截图。
- 看板定义加载 → 状态兼容性校验 → 状态恢复完成 → 卡片取数 → 时间信息及图表最终帧完成 → 截图。
- 增加 `viewStateReady` 等明确握手，避免先按默认条件查数后过早截图；恢复阶段屏蔽默认查询。
- 业务查询失败、视图不兼容、必要卡片未完成时不发送。业务时间 SQL 获取失败可按迭代一规则明确展示。
- 第一版只快照筛选，Tab 使用报表默认选择，图例使用默认展示；表单说明“保存筛选条件”，不能承诺保存所有视觉操作。
- 未来支持 Tab 后，只截图每个分组选中的页面；非选中的 Tab 不阻塞截图。需导出全部 Tab 时再定义另一项功能。
- 自动截图不使用个人默认、浏览历史或浏览器旧存储，也不更新最近访问。
- 运行记录提供条件摘要和执行日期范围，便于排查“邮件内容与预期不同”。
- 状态已失效的订阅应显示“需要更新条件”，暂停自动发送；使用现有可见失败／停用入口，错误原因要区别于临时网络失败。

### 4.7 拟议数据结构与接口

| 表 | 主要字段／约束 |
| --- | --- |
| `vis_dashboard_user_pref`（新增） | `user_id`、`dashboard_id` 联合唯一；`favorite`、`last_viewed_at`、`default_view_id` |
| `vis_dashboard_user_view`（新增） | `id`、`user_id`、`dashboard_id`、`view_name`、`state_json`、`bindings_json`、`revision`、审计字段（视图删除为物理删除） |
| `vis_dashboard_subscription`（扩展） | `view_state_json`、`view_bindings_json`；可选来源视图 ID 仅用于溯源，不用作运行时依赖 |
| `vis_dashboard_subscription_run`（扩展） | 入队状态快照、绑定快照、`as_of_date` 日期基准、运行时区；重试复用 |

偏好唯一键保证每用户每报表只有一个个人默认；设置默认时校验视图的用户和报表一致。删除默认视图后清空该默认引用。保存视图使用 revision 防止跨标签页互相覆盖。

接口按现有项目风格增加：个人报表列表（收藏／最近）、幂等设置收藏、记录访问、个人视图列表／保存／删除／设置默认、解析视图状态、订阅内容保存与运行状态读取。统一使用现有 `R<T>`、ID 字符串约定。

所有接口从登录上下文确定用户，读写均检查当前看板可见性。撤权或禁用的报表从个人列表过滤；直接链接仍由后端拒绝。筛选状态经过看板定义和绑定白名单验证后才能转成查询条件。

### 4.8 验收重点

- 收藏、最近访问、个人视图在刷新页面、重新登录及不同设备间一致，用户之间隔离。
- 收藏不保存筛选；取消收藏不删除视图；订阅不会产生最近访问记录。
- 命名视图可更新、另存、设默认、删除；临时筛选不覆盖已保存视图。
- 显式 URL、个人默认、公共默认的优先级正确，显式清空得以保留。
- 重命名标签保持兼容；删除字段／改变绑定／类型变更不能默默扩大取数范围。
- 同一报表两个不同筛选的订阅收到不同内容；修改／删除来源视图不改变订阅。
- 修改订阅后已入队任务保持原条件，后续任务使用新条件；重试跨午夜仍使用同一日期范围。
- 恢复状态前不触发默认截图，普通与透视卡片都应用订阅筛选和日期基准。
- 邮件中的条件、日期、截图、链接一致；链接重新查询时明确数据可能已变化。
- 旧订阅和旧 `f` 链接有明确兼容行为。

## 5. 交付顺序与边界

| 迭代 | 建议实现顺序 | 交付结果 |
| --- | --- | --- |
| 一：时间 | 时间定义／DTO → SQL 配置和服务 → 卡片时间与刷新状态 → 截图与邮件时间 | 用户能分清结果何时刷新、源数据何时更新，以及刷新是否失败 |
| 二：个人使用 | 视图模型与兼容校验 → 收藏／最近入口 → 筛选视图和默认 → 订阅与运行快照 → 截图恢复和邮件链接 | 用户能快速打开常用报表、保存自己的筛选，并持续收到对应内容 |

迭代二依赖第一期时间展示用于邮件说明，但不应把时间值写入个人视图。两个迭代分别验收、分别交付。

本次范围外：Tab／图例持久化实现、个人布局编辑、视图共享权限体系、查询结果缓存、异常阈值告警、报表配置版本发布。它们不应阻塞这两期。

实施时更新 `backend/db/schema.sql` 的结构快照，遵循项目不维护增量迁移文件的约定；初始化脚本会重建表，不能直接拿它更新有业务数据的环境。存量环境应在实际实施时单独确认和执行非破坏性的结构变更。

必要检查：后端相关语义和权限测试、前端状态恢复／竞态／订阅截图测试，以及项目规定的 `mvn test`、`pnpm lint`、`pnpm type-check`。实现包含前后端功能、原始 DDL 和自动化回归测试。


## 6. 本地验收与使用

- 报表中心首页沿用原插图，下方放收藏与最近访问两个紧凑列表；全部报表仍从左侧分组进入。
- 数据集编辑页的“数据更新时间”可配置、测试 SQL。示例数据集“零售订单明细”已配置日期精度的 `SELECT MAX(order_date) FROM dwd_retail_order`，作为该演示数据快照的截止日期示例；真实业务应使用经确认的批次完成时间。
- 看板更多菜单可收藏；刷新按钮左侧切换、保存和管理个人视图。顶栏操作按悬停、键盘聚焦或触屏点按显示，筛选常驻；每用户每报表最多 30 个视图，名字最多 80 字。
- 链接筛选独立恢复并明确标记；个人视图暂不保存 Tab 与图例。
- 订阅内容可选当前筛选、公共默认、个人视图。编辑时“保留订阅原有条件”不重写快照或绑定。
- 订阅回看显示固定条件、日期基准和实时重查提示；查询、透视、明细及导出都由后端强制绑定到运行快照。
- 业务时间 SQL 的只读连接、单条 SELECT、三秒查询超时和一行一列校验已启用。并发查询仅合并同用户同数据集配置的正在执行请求，没有结果缓存。
- 本地已有表已调整，原始 `schema.sql` 同步更新，没有新增迁移文件。未启用自动邮件发送；SMTP 和订阅开关继续使用现有部署配置。

已覆盖的自动化验证：时间解析和 SQL 约束、空值与失败隔离、视图显式清空／绑定变更、用户归属与并发版本检查、真实 MySQL 中的默认引用和运行快照、普通／透视／明细运行绑定、前端刷新竞态与恢复优先级，以及截图服务的恢复握手和失败中止。
